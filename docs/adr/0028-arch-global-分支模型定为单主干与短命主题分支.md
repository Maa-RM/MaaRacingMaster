# ADR-0028（arch-global）：分支模型定为单主干与短命主题分支，PR 准入按「命名硬拦、体积软线、门禁自伤硬检」

- **状态**：`accepted`
- **日期**：2026-11-24
- **决策者**：用户（确认「单主干 + 短命主题分支 + 压扁，我找不到更强的反例」）
- **相关**：[AGENTS.md](../../AGENTS.md)「绝对红线」「作业纪律」、[`skills/project-update/SKILL.md`](../../skills/project-update/SKILL.md)「分支模型」、[ADR-0006](./0006-meta-adr-决策粒度只收跨模块约束.md)、PR [#25](https://github.com/Maa-RM/MaaRacingMaster/pull/25) / [#27](https://github.com/Maa-RM/MaaRacingMaster/pull/27)

## 背景

旧模型是「长期个人草稿本 + 压扁沉淀」：日常 commit 全落一条按人命名、长期不结束的分支（`dev/d542Bb`），稳定线只收经过压扁的主题提交。它在单作者、强迭代期成立，但积累了三类结构性代价：

1. **冲突判据失真**：稳定线每个点是压扁产物，与草稿线的详细历史之间没有可自动判定的合并基线。上个 tag 之后首次沉淀，PR 会报出几十个「内容并不冲突」的假冲突；一次收口实测 28 处冲突，其中 20 处来自待发提交、正确一侧是草稿线，8 处才是稳定线的独有内容。人工逐文件裁决会增加出错面，必须靠「树是否相等」这类外部证据来分流。
2. **并行会话没有隔离**：一条长期分支只有一个 HEAD，多个会话共用一个工作树与暂存区，「谁的提交落到哪条分支」只能靠自律。多会话同时工作时，`amend` / `checkout` 都会掀掉别人的内容。
3. **历史形状与交付节奏脱钩**：草稿线一个主题结束没有明确的落点信号，收口时机靠人想；压扁前的整理总发生在「已经堆了几十个提交」之后。

单主干模型的目的不是「更好看的历史」，而是**让每个 PR 的净增量可被独立复核**：分支从 master 切出、只含一个主题、合入即删，净增量就等于这个主题本身，不需要任何集成提交或假冲突分流来「造」一份可审的对照物。

## 决策

1. **单主干**：`master` 是唯一长期分支，历史线性、一个主题恰好一个压扁提交。稳定线写入只经 PR，规则集锁定为 squash 合并，`merge commit` 与 `rebase merge` 在仓库设置层关闭。
2. **主题分支短命**：一切工作从 `origin/master` 切出 `type/slug`，主题收口即合入并删除。命名取 [Conventional Branch](https://conventional-branch.github.io/)：类型闭集 `feat` / `fix` / `chore` / `hotfix` / `release`，slug 全小写、字符集 `[a-z0-9.-]`、不按下划线分段。`dependabot/**` 为机器生成的豁免；打 tag 前的最后收口才用 `release/<版本>`。
3. **历史例外只留一条且只读**：旧草稿线的**归档引用**永久保留（远端 ref 名由 `archive` 前缀与旧线名 `dev-d542Bb` 组成），用于让旧线的提交在远端仍可解析。它是**一次性例外**：不新增、不写入、不当作合并源；新的长历史一律不再产生。
4. **工作隔离以主题为单位**：一个主题一个 worktree，共享检出里 HEAD 只停在该主题分支上，任何会话都不在共享检出里 checkout `master`。共用 `.venv` 为只读约定：worktree 内不建环境，测试与门禁显式用 `<共享检出>\.venv\Scripts\python.exe` 指向共享环境。
5. **PR 准入三道闸**，机器只拦可判定的两条：
   - **命名**：头分支不匹配第 2 条即红（`dependabot/**` 豁免）。这是唯一能零歧义机检的形态约束。
   - **体积**：只警告不阻断。越软线（>400 行或 >20 文件）在 PR 里提示，要求在描述中说明为何不能拆。**不做硬门槛**——本仓库自己的收口 PR 就在 342 行 / 14 文件与 +1192 行 / 26 文件，硬门槛只会逼出「拆成看不见全貌的碎 PR」「藏进顺手格式化」「绕过门禁」三类规避。
   - **门禁自伤**：同一 PR 既改 `.github/**` 的门禁定义（workflow、必需检查相关）又在测试上做减法（删除用例、加 skip、放宽断言）时强制人工复核。这一条比体积重要：它挡的是「为变绿改门禁」。
   - 「一个 PR 一个主题」**不做机检**（机器判不了主题一致性），留在政策文本，由评审判断。
6. **寿命是约定不是闸**：主题分支的目标寿命约两天，跨周工作（如 NavKit v4 这类架构迁移）按**可交付里程碑**拆成多条分支，每条都能独立合入 master 并保持可运行；不设自动过期检查。
7. **证据锚分两级**：交付级锚 tag 与 PR 号，内容级锚 master 可达的提交。**主题分支提交不得作为正式知识层的证据锚**——分支合入即删，它的提交不在任何常规 ref 上，写入等于让每个新 PR 重新制造「只能靠 archive 保活」的指针。

## 后果

**收益**：

- PR 净增量即主题本身，不需要集成提交、不需要「树相等」证明、不再出现假冲突分流；复核对照物天然存在。
- 并行会话按主题分 worktree，提交落点由工作树决定而非 HEAD 约定；「提交跑到别人分支上」这类事故从机制上消失。
- 收口时机由分支寿命给出信号：一个主题一条分支，合入即删，不留「什么时候该整理」的悬置判断。
- 命名与门禁自伤可机检，评审注意力从「格式对不对」转向「内容对不对」。

**代价与约束**：

- **不能再用「一条草稿线并行多主题」**：多主题并行必须多条分支 + 多个 worktree，重建与清理成本上升；占位 worktree 需要显式回收。
- **分支命名成为硬约束**：写错的头分支开不出 PR（`dependabot/**` 除外）。临时试错分支必须按规范命名，或直接不留远端。
- **`--admin` 仍是既有通道**：传统分支保护的 `enforce_admins` 为 `false`，仓库所有者可在检查未绿时绕过。本决策不关闭该通道（发版收口与紧急修复需要），只要求「逐次确认」。
- **必需检查在两处登记**：`stable-master-pr-only` 规则集与传统分支保护同时持有 `单元测试 (pytest) (3.11)`。今后若退役传统保护，**必须先在规则集里确认该检查存在**，否则会连带删掉 CI 门禁且没有任何提示。
- **体积软线会常态化越线**：收口类、资源模板批量更新类 PR 天然超标，警告数量不会归零；这被接受为「提示通道」而非「质量信号」。

**被否方案**：

- **长期草稿线（旧模型）**：假冲突与并行写者两类问题无解，已由 #25 / #27 的实测代价证明。
- **真 merge 节点进 master**：保留双向历史换取「无假冲突」，代价是 master 失去线性、压扁语义与一行一主题的可扫读性；用户明确否决。
- **按人命名分支**（`dev/<用户名>`）：把并行度绑在人数上，单作者时退化为旧模型，多作者时无法表达主题边界。
- **「合并重建 + 重新分离」的集成提交**：为制造一份可审对照物而构造中间提交，属于为工具的形状服务；单主干后对照物由 PR 自身提供，该方案随旧模型一并退役。
- **硬性体积门禁**：见决策 5，会逼出规避行为而非小 PR。
- **主题分支提交作为证据锚**：与「合入即删」直接冲突，等于让 archive 例外常态化，违反决策 3。

## 证据

- 一手核查：[Conventional Branch 规范](https://conventional-branch.github.io/)（类型前缀与字符集）；[Google 小 CL 指南](http://google.github.io/eng-practices/review/developer/small-cls.html)（体量为软线，由评审者判断，不设自动拦截）。
- 机检背书：规则集 `stable-master-pr-only`（`pull_request` 仅允许 squash、`required_approving_review_count: 0`；`required_status_checks` 含 `单元测试 (pytest) (3.11)`，`integration_id 15368`）；仓库设置 `delete_branch_on_merge=true`、`allow_merge_commit=false`、`allow_rebase_merge=false`。
- 实证：旧模型收口的实测代价——`dev/d542Bb` → master 合并报 28 处冲突（20 处取草稿线侧、8 处取稳定线侧、含 3 张 PNG 二进制 add/add），合并结果相对草稿线原树只增 14 文件 +243/−99，相对 master 为 22 文件 +1164/−107（PR [#27](https://github.com/Maa-RM/MaaRacingMaster/pull/27)）。
- 实证：归档引用指向 `ff2b50f`，合入 PR #27 后远端旧线分支被 `delete_branch_on_merge` 自动删除、归档引用仍存在；证明「合入即删」与「历史例外保活」可以并存。
- 机检：PR 准入闸由 [`.github/workflows/branch-conventions.yml`](../../.github/workflows/branch-conventions.yml) 承担（`pull_request` 触发，`tools/pr_conventions.py` 实现判定，`tests/test_pr_conventions.py` 守判据）；体积越线只以 `::warning` 呈现、退出码仍为 0，命名与门禁自伤返回 1。检查名登记进规则集 `required_status_checks` 之前，它只是红色提示、不阻塞合并。
