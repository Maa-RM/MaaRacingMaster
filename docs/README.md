# docs — 信源文档根

> **本文是什么**：`docs/` 的目录索引与**文档写作规范**——有哪些文档、各是什么信源等级、新文档怎么写（文档头 / 指针纪律 / 数值禁令 / plan 规范）。
> **本文不是什么**：不是项目导航（见 [CODE_WIKI.md](./CODE_WIKI.md)）；不是协作守则与知识路由（见 [AGENTS.md](../AGENTS.md)）；不是架构决策的理由（见 [adr/](./adr/README.md)）。
> **信源等级**：L1（写作规范部分）/ L3（索引部分）—— 可作「文档怎么写、该放哪」的直接依据；不得作为技术事实的依据（回其 home）。
> **继承**：通用协作与信源规则见 [`AGENTS.md`](../AGENTS.md)；本文只补充文档写作特有的约束。

## 文档写作规范

### 文档头

正式知识文档（L1 / L2）在文件开头声明自己：

```markdown
> **本文是什么**：承载哪类知识、以什么问题为对象。
> **本文不是什么**：哪些内容不在这里建立第二份真相（指向其 home）。
> **信源等级**：Lx —— 可作哪类问题的直接依据；不得作哪类问题的最终依据。
> **真源路由**：本文依赖的事实，其真源在哪。
> **继承**：通用协作与信源规则见项目根的 `AGENTS.md`（**按本文所在层级修正相对路径**）；本文只补充本对象特有约束。
```

L3 / L4 导航型文档可省去「真源路由」一行。**只声明与指向，不复制** AGENTS 的通用规则——同一规则抄在许多份文件里，就是许多份会各自腐坏的真源。

### 不得抄录可机检的真源数值

凡能被 JSON / 代码单向算出的值（阶段数、计数、清单长度），prose 只写**指向真源的路径**，不写数值本身；枚举清单同样换成指向，写指针时也不带数量。手抄数字没有守卫就必然腐坏。
机检形态：[`tests/test_doc_no_copied_numbers.py`](../tests/test_doc_no_copied_numbers.py)。
CODE_WIKI 正文的过程残留（日期 / 会话戳 / 轮次 / 阶段代号 / step / 迁移期号 / 计数快照）另由
[`tools/check_repo_hygiene.py`](../tools/check_repo_hygiene.py) **R11** 棘轮守卫：存量入基线、
新增即红，历史证据按 [AGENTS.md](../AGENTS.md) 红线 6 的三类口径留痕（不一律指 commit）。归档区 CODE_WIKI（历史快照）与 ADR / update_log 的合法历史叙述不在面内。

### Why 归属

**对象决定文件，不是 Why 决定文件**：项目级架构为什么这样定 → [adr/](./adr/README.md)；模块为什么这样实现 → 该模块 `CODE_WIKI.md`；子系统为什么这样施工 → 其 `README.md`；局部代码为什么不能改成另一种写法 → 代码注释 / 结构。

### 指针纪律

跨文档只给指针，不复制真源。改路径时**链接文本与 URL 两侧都要核**；章节号会漂，指针写「去哪个文件的哪一类内容」比写死节号更耐用。

**同一条规则在文内也只写一处**，其余位置只做索引：状态表与操作步骤并列描述同一件事，改一边忘一边，读者就会读到两种行为（性能契约落地时真实发生过）。表格写「状态是什么」，步骤写「怎么做」，不互相复述。

### update_log 收录判据

[`update_log.md`](./update_log.md) 是**面向玩家的更新说明**（Release 正文信源），不是开发日志；唯一读者是玩家。

**写每一条前自问：玩家装上新版后能看到、感到什么不同？** 答得出就写，答不出就不写。

- **写**：新功能、界面与交互变化、行为变化、操作更跟手、启动更快、包更小、报错更清楚、新增可选开关。
- **不写**：内部重构与模块拆分、测试与 CI、文档与规则、实验与探针、内部协议与接口、代码整洁、性能测量值本身（玩家能感到时改用感受描述）。
- **不出现**：文件路径、类名 / 函数名、测试计数、commit 哈希、实验代号、统计量（AUC / p 值 / 中位帧间隔）。
- **组织**：按「新增 / 改进 / 修复 / 移除」分组，每条一句话，用玩家的语言；没有的组不写。
- **未发布改动不进本文**（它还不是「更新」）：发版时从 `git log <上个 tag>..HEAD` 提炼——过程细节已在 commit message。
- **纯内部版本**保留小节标题并写「本次为内部调整，玩家无可见变化」，版本序列不断档。

## plan 规范（`docs/plan/`）

`docs/plan/` 是**工作台，不是知识库**：AI 生成的实施计划、方案对比、验证报告落这里，gitignore 不入库。

**新建一律从模板起笔**：[`templates/plan/PLAN_TEMPLATE.md`](../templates/plan/PLAN_TEMPLATE.md)。头部三行是硬要求（机检 [`tools/check_repo_hygiene.py`](../tools/check_repo_hygiene.py) R6）：`状态` / `归属去向` / `退役条件`，占位符原样留着算未填；`更新` 可选，填了台账的未动天数才准。`落地锚` 在状态为 `retiring` 时必填，且必须含 PR 号或提交哈希——退役要回答「这份方案的哪一部分落在了哪个交付上」，只写「已实施」复核不了。

### 状态只有两个值

- **`active`**——在树里就说明还有未闭环的事：评审中、待实施、实施中。
- **`retiring`**——结论已迁到 home、或未落地的部分已转成 issue / 转给下一条 plan，正在走下面的退役四步；此时头部必须带可复核的 `落地锚`。

**没有 `done` / `已完成` / `archived`**：plan 的"完成"不是一种状态，**离开活树才是**——终点是移入 `_retired/`（见下）。写下"已实施"却留在活树里，是本区唯一的病——它既不是知识（不能引用），也不是待办（没人再看），只是占着位置，让下一个人误以为这里有活要干。

**不要求 100% 完成才退役**：设想没有全部落地时，把未完成的部分写成 issue（`label: self-todo`）或在 `归属去向` 里指向接手的下一条 plan，就可以退役。留在活树里等「哪天做完」，比转成 issue 更贵——下一个人会以为这里有人在推。

### 退役四步（顺序不可换，与实验区出口同构）

1. **结论迁 home**：成立 / 不成立 / 条件成立的最终结论写进「归属去向」那一行填的地方（ADR / 某个 `CODE_WIKI.md` / `RULES.md` / issue），证据指针按 [AGENTS.md](../AGENTS.md) 红线 6 的三类口径写，不写 plan 路径。**没做完的部分**在这一步转成 issue 或写清「下一条 plan 承接」，不留悬空。
2. **资产提升或随删**：plan 引用的脚本、数据、探针，仍被消费的移入 `tools/` 正式位或消费它的插件并改好引用；没人用的随文件一起走。判据同"第二个使用者"：今天真实存在才提升。
3. **拔引用**：全仓 grep 文件名，L0~L3 文档与生产 / 测试 / 运维代码零命中（R3 是这一步的验收）。
4. **转移**：移入 `docs/plan/_retired/`，文件名保持原样；头部状态留 `retiring`，`落地锚` 填到前面填好（PR 号 / master 提交哈希）。`_retired/` 里的文件**不再计入台账、不得被任何文档引用**，只作「当时怎么想、试过什么」的历史比对。

> 为什么是转移而不是删除：plan 不入 git，删掉就真的没了——半年后想回查「当时为什么否掉这个方案」只能重造。转移的代价是该目录会慢慢变厚，且它只存在于当前这台机器上（gitignore），所以它**不是知识**：谁要引用结论，回 home 读已经提炼的那份。

模板末尾内嵌了这份清单：**打开任何 plan 文件都能看到它自己的出口**，不必回头查这一节。检查器每次运行还会打印工作台账（状态 + 未动天数），让"没人删"持续可见，而不是静默豁免。

### 其余约束

- **只能向上产出**：plan → ADR / CODE_WIKI / 指南 / 实验 / issue / 生产实现。长期价值只存在于被提炼的产出里；plan 本身不是任何知识的住户。
- **禁止反向引用**：正式文档（L0~L3）与生产/运维代码不得引用 `docs/plan/` 下的具体文件（机检 R3）；实验引用 plan 只作过程指针、不作事实依据。
- **`_retired/` 是本地归档，不是知识**：它保留退役 plan 的原文用于历史比对（plan 无 git 历史，删了不可恢复），代价是目录会积累、且只存在于当前这台机器上。因此：不作为任何结论的依据、不被 L0~L3 文档或代码引用（R3 同口径）、不计入台账。历史若重要，留结论在它产出的 issue / commit / 最终文档里，而不是留原文。
- 较大改动的 plan 以行为契约开头：先定行为再谈技术方案，段次、骨架与每格准入判据见 [`templates/plan/BEHAVIOR_CONTRACT_TEMPLATE.md`](../templates/plan/BEHAVIOR_CONTRACT_TEMPLATE.md)；跨层、新模块、并发与资源类改动必写。
