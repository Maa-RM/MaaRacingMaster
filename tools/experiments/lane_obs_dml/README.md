# lane_obs_dml — 线观测的算力账与 DML 迁移

## 背景

线观测（TwinLiteNet+ Small，`lane/plus_small_384x640.onnx`）现役跑 CPU 4 线程、
控制拍（20Hz）逐拍检测；配置注释的口径是「约 23ms/帧，仍在 50ms 控制拍内」。
同进程的感知与深度都跑 DML，受 `core/dml_lock` 全局互斥（并发 DML run 会段错误）。
2026-10-24 的结论是「线观测也走 DML 会与深度相位锁，深度连续丢 95% 帧」，因此
provider 缺省固定为 cpu。

用户反馈整机 CPU 偏高，要求回答：这么小的模型（0.54MB）为什么这么吃算力？
换 DML 值不值、会不会重新饿死深度？

## 要回答

1. 模型「小」在哪、算力花在哪——参数量、FLOPs、逐节点耗时；
2. 生产环境里线观测实际占多少 CPU、每帧多久（用历史 `perf.jsonl` / trace 对账）；
3. 同模型换 DML 后省多少；共用 DML 锁对深度与控制拍的实际代价。

## 方法

`probe_lane_dml.py` 自包含重建生产调用面（不 import 业务代码）：

- 会话参数照抄生产：线观测 `intra=4 / inter=1`（cpu 与 dml 两份），感知与深度
  各按 `build_session_options` / `load_session` 同参；
- 帧源：真实对局 raw 帧（`speedrush_depthart_prod` 的 1280×720，循环喂）；
- ① 单帧阶段成本；①b 线程数 × ORT 自旋矩阵；② 感知 20Hz 持锁 + 深度 60ms
  错峰 + 线观测（off / cpu / dml 非阻塞 / dml 阻塞 / dml 阻塞 10Hz）五场景；
- 生产对账：历史会话的 `perf.jsonl`（1Hz 采样，线程 CPU/未归因）与
  `trace/speedrush.jsonl`（逐拍 `lane_obs.ms`）；
- 模型账：ORT profiler 单线程逐节点耗时 + ONNX shape inference 估 FLOPs。

**测量环境陷阱（2026-11-13 实测）**：从 IDE 子进程直接跑探针时，Windows 会给
进程套上「能效节流」（EcoQoS, `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`）：
同一帧 4 线程前向 417ms / CPU 400ms，显式退出节流后 26.7ms / 93ms，线程数
的扩展性也恢复正常。脚本启动时已显式退出节流并打印状态；未退出时的数字全部作废。

## 结果

2026-11-13，本机（RTX 4060 Laptop / 12 逻辑核），真实对局帧 14 张循环；
整机 CPU（含本探针）p50 65~100%，游戏与 IDE 同期在跑。

### ① 模型账：参数小 ≠ 算力小

- 122,089 个参数、0.54MB，但**每帧 2.53 GFLOPs**（91 个 Conv）；
  最大的一层是 67→67、3×3、96×160，单层 1.24 GFLOP，占全模型一半；
- 单线程前向 53~55ms，逐节点合计 52.9ms：Conv 35.8、PRelu 8.2、布局重排 2.8、
  ConvTranspose 1.8、Concat 1.2、BN 1.1；
- 4 线程前向：墙钟 23.2ms、CPU 89.1ms——20Hz 光前向就要约 1.8 核。

### ② 生产对账（历史会话）

| 会话 | 线观测 ms p50 / p90 / p99 / max | 连续段检测频率 | 进程 CPU（单核） | 线观测线程 CPU |
|---|---|---|---|---|
| 20261112_220717 | 36.9 / 43.7 / 52.6 / 136.6 | 19.4~19.7Hz | 473% | 69% |
| 20261113_083813 | 38.4 / 44.2 / 54.7 / 163.3 | 19.7Hz | 495% | 69% |
| 20261113_120841 | 39.1 / 47.5 / 61.0 / 159.9 | 19.6~19.7Hz | 495% | 72% |

- 待机时进程 CPU 0.04 核、线观测线程不在；一开跑进程 4.8~5.0 核，
  其中约 3.2 核是**未归因的原生线程**（ORT 线程池 + OpenCV），线观测自己的
  线程约 0.7 核；按每帧 112ms CPU × 20Hz 折算，线观测整体约 **2.2 核**。
- 每帧 37~39ms 已占满 50ms 控制拍的四分之三，p99 55~61ms——**它不是「顺便跑」，
  而是持续吃两个多核，且单帧延迟已经超出控制拍预算**。

### ③ 单帧阶段成本（重复 20 次取均值，已退出节流）

| provider | pre（wall/CPU） | run | decode | extract | badge | 整帧 p50 | 整帧 CPU | 20Hz 需核数 |
|---|---|---|---|---|---|---|---|---|
| CPU 4 线程（现役） | 0.7 / 3.1 | 21.2 / 84.4 | 0.7 / 3.1 | 4.3 / 18.8 | 0.5 / 0 | **27.5ms** | **111.7ms** | **2.23 核** |
| DML | 0.7 / 3.1 | 5.7 / 21.9 | 0.7 / 3.1 | 4.4 / 18.8 | 0.5 / 0 | **11.4ms** | **44.5ms** | **0.89 核** |

阶段 CPU 会被 ORT 线程池的余热污染（extract 的 CPU 大于墙钟），总量以整帧为准。
DML 省的是前向那 60~70ms CPU；后处理（decode+extract+badge）不变，仍约 20ms/帧。

### ④ 线程数 × ORT 自旋（同一帧，run p50 / CPU，已退出节流）

| threads | spin=default | spin=off |
|---|---|---|
| 1 | 55.1 / 53.1 | 53.2 / 52.3 |
| 2 | 30.7 / 61.7 | 31.1 / 68.8 |
| 4 | **23.2 / 89.1** | 22.9 / 100.0 |

退出节流后线程数按预期扩展，自旋开关差异在噪声内。**未退出节流的进程里，
线程数越多越慢（4 线程可慢到 8 倍），这类数字不能用来评价生产配置**——复算前
先确认首行打印的节流状态。

### ⑤ 生产节拍下的锁争抢（12s/场景）

| 场景 | 感知 run p50/p95 | 深度成功/实际 Hz | 线观成功/实际 Hz | 进程 CPU（单核） |
|---|---|---|---|---|
| off（基线） | 5.8 / 9.1 | 98% / 15.4 | — | 42% |
| cpu（现役） | 6.8 / 16.7 | 79% / 10.4 | 100% / 10.2 | **176%** |
| dml 非阻塞 20Hz | 6.2 / 11.9 | 96% / 15.7 | 68% / 13.5 | 58% |
| dml 阻塞 20Hz | 5.9 / 9.0 | 80% / 13.3 | 100% / 20.0 | 54% |
| dml 阻塞 10Hz | 5.6 / 9.6 | 85% / 14.0 | 100% / 10.0 | **41%** |

（各场景整机负载不同，见「边界」。）

### ⑥ FP16 线观测的锁争抢（现场转换 FP16，10s/场景）

| 场景 | 感知 run p50/p95 | 深度成功/实际 Hz | 线观成功/实际 Hz | 进程 CPU（单核） |
|---|---|---|---|---|
| off（基线） | 6.2 / 9.1 | 100% / 16.6 | — | 39% |
| dml 阻塞 20Hz（fp16，run 4.0ms） | 6.0 / 8.3 | 75% / 12.4 | 100% / 20.0 | 46% |
| dml 阻塞 10Hz（fp16） | 5.9 / 7.7 | 88% / 14.3 | 100% / 9.8 | 43% |

FP16 把取锁时间从 6.3ms 压到 4.0ms，但 20Hz 下深度仍丢约 1/4 的尝试；
这里深度 worker 只跑 pre+run（全链约 7.4ms，实测 16.6Hz），**不等于生产深度
链的最终出帧率**——生产链约 38ms、名义 10Hz，锁争抢的最终影响要用完整深度链
离线回放才能定论（同样不需要实机）。

### ⑦ 固定排班（`--slots`，离线模拟）

目标：深度 10Hz、感知与线观测 20Hz，三者共用一把 DML 锁且不互相抢。

**排班表**（每 50ms 一拍；深度只在偶数拍）：

| 拍型 | 槽位（拍内顺序） | 内容 | 锁外并行 |
|---|---|---|---|
| 每拍 | 0 ~ 8ms | 感知（控制线程阻塞持锁） | 线/深预处理在拍内提前做（0.7 / 1.5ms） |
| 每拍 | 感知放锁后 | 线观测（FP16，约 4ms） | 线后处理（约 4ms） |
| 偶数拍 | 线观测之前 | 深度（约 6ms） | 深度后处理（约 30ms） |

偶数拍把深度排在线的前面：深度前向先跑，它的 30ms 后处理与线观测的 GPU 运行
并行，两者都不越过本拍；奇数拍只有感知 + 线观测。交接用「槽位令牌」——感知
放锁时把锁交给下一个槽，不排队、不抢锁；控制线程只等感知，不等后面两槽。

每个槽有截止时刻（线 35ms、深 40ms，按拍起点算），过点即跳过本拍（线/深都是
latest-only），下一拍重新对齐，避免一次慢拖三拍。

**模拟结果**（12s / 241 拍，FP16 线观测，真模型 + 真帧）：

| 消费者 | 达成 | GPU 耗时 p50/p95 | 槽延迟 p50/p95 | 结果就绪 p50/p95 | 消费帧龄 p50/p95 |
|---|---|---|---|---|---|
| 感知 | 241/241（20Hz） | 5.7 / 8.0 ms | 0（控制线程第一段） | 拍内 | ~0（同拍消费） |
| 线观测 | 241/241（20Hz） | 4.1 / 6.2 ms | 18.2 / 28.3 ms | 29.1 / 38.1 ms | 50 / 50 ms |
| 深度 | 119/120（10Hz） | 5.5 / 8.1 ms | 15.3 / 23.1 ms | 52.6 / 59.0 ms | 100 / 100 ms |

帧龄按「模块每拍开头读 latest」折算：结果在下一拍读之前就绪就是一拍龄，
否则顺延一拍。线观测稳定吃一拍（50ms），深度吃两拍（100ms，预算 350ms）。
GPU 占用 26.4%，进程 CPU 0.52 核（模拟进程），零服务丢帧。

口径说明：模拟里的控制线程会等三个槽跑完（整拍 p50 23.5 / p95 32.7ms）；
实际实现中控制线程只等感知（约 8ms），线/深槽由线程异步交接，不占控制拍。
深度后处理用 30ms 固定延迟建模（真实链约 38ms），最终数值需用完整深度链复核。

## 结论

1. **「小模型」是误会**：0.54MB 只是权重，算力由分辨率×通道决定——每帧
   2.53 GFLOPs，一半集中在一个 67→67 的大卷积；20Hz 意味着 50 GFLOP/s 的持续负载。
   生产 trace 的 37~39ms/帧与它吻合，这不是配置错误，是模型本身的量级。
2. **生产 CPU 账**：跑图时程序占 4.8~5.0 核（待机 0.04 核）；线观测约 2.2 核
   （0.7 核调用线程 + 约 1.5 核 ORT 原生线程），是程序内最大的单项。
3. **换 DML 值**：同一帧整帧 CPU 从 112ms 降到 45ms（20Hz 从 2.23 核降到 0.89 核），
   墙钟 27.5ms → 11.4ms，检测率不再被拍长卡住。
4. **共用锁不再致命，但要限频**：20Hz 阻塞取锁让深度丢约 20% 帧（15.4→13.3Hz），
   10Hz 只丢约 15%（14.0Hz），感知拍长与基线无差。2026-10-24「深度只剩 5%」
   未复现——当前深度链（v5 448 + 错峰节拍）已不同。
5. **性价比排序**：`detect_every=2`（10Hz，CPU 直接减半，不改 provider）→
   DML（再省一半 CPU 且不占控制拍）→ 两者并用（进程 41% vs 现役 176%）。
   后处理约 20ms/帧没优化，是下一刀的落点；模型侧最大头是那个 67→67 卷积，
   动它要重训+评估，不在本次范围。

## 边界

- 争抢模拟只有感知/深度/线观测三方；真实进程还有采集、预览、调试落盘与更重的
  控制拍 Python 负载，控制拍余量应按本实验偏乐观估计。
- 「整机 CPU」含本探针自身；各场景外部负载 65~100% 不等，成功率可横向比，
  绝对毫秒不要跨场景比。
- 后处理耗时含 ORT 线程池余热，阶段分账只作方向参考，总量以整帧 CPU 为准。
- 生产对账的「连续段检测频率」按计数器不倒退的连续段（>5s）计算，排除换局/换阶段
  时 `det_n` 归零造成的假低值。
