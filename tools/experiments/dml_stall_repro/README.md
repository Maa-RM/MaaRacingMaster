# dml_stall_repro — 开车中 1 秒级推理停顿的离线复现台

## 背景（2026-11-07 流水诊断）

最近多场 speedrush 对局出现 1 秒级整体停顿（11:05:56 / 12:08:40 / 14:55:30 各一次，
0.9~1.3s）：停顿拍感知单次推理从 ~8ms 冲到 0.8~1.1s（持 DML 锁期间），深度观察同拍
缺位（锁被占、Busy 跳帧），调试图落盘 143~303ms（正常 ~15ms），采集链 1.24s 零新帧。
游戏侧计时与场景照常推进。常态 20Hz 拍 p95 72~78ms（预算 50ms）。

用户补充事实：游戏是手机游戏（模拟器/客户端负载极小）→「游戏抢满 GPU」假设降权，
嫌疑转向本进程内部（DML 会话互斥、显存水位、CPU 饥饿、盘 IO）。

已知前科（代码内注释）：
- 并发 DML run 段错误（2026-09-25）→ 全局锁串行，感知阻塞持有、深度 Busy 让锁；
- 显存吃紧时普通 run 触发显存分页，单帧 59→136ms（2026-10-01，8GB 卡水位逼近上限）；
- 一次深度前向 ~54ms 不可分割，错峰节拍（TICK_BEAT）压伸出量。

## 待复现问题（判据）

复现成功判据：**离线（无游戏、无采集）单进程内，感知会话单次 run 耗时 > 500ms**
（生产观测 799~1071ms；正常 ~8ms），且可稳定重复出现。100~500ms 记为弱复现。

## 方法

`repro.py` 自包含重建生产调用面（不 import 业务代码）：
- 感知会话：与 `core/yolo_detector.py` 同参构造（图优化全开、内核缓存、intra/inter=4、
  DML→CPU），输入 640×640 letterbox，持锁 run；
- 深度会话：与 `plugins/speedrush/depth_geo.py::load_session` 同参（自由维折叠 1×720×1280，
  DML→CPU），普通 run（生产 IO binding 是条件路径，先复现普通路径）；
- 锁协议：threading.Lock + 错峰节拍（感知放锁记拍，深度 worker 等新拍后开工，
  抢不到锁弃帧）；
- 节拍：感知 20Hz（50ms 预算），深度默认 160ms 间隔；
- 帧源：真实对局 raw 帧（debug 目录 720×1280 JPEG）循环喂；
- 独立标尺：nvidia-smi 500ms 轮询（利用率/显存/温度/频率），与停顿时刻对齐。

### 机制取证（V7b 停顿窗口，nvidia-smi 0.5s 轮询独立标尺）

- 停顿前 1 分钟：GPU 利用率顶死 94~99%、显存 7457~7487/8188MiB、功耗 77W；
- 停顿瞬间恰逢一次 churn（显存 7458→6852→6894MiB）：GPU 利用率归 0、功耗塌至
  25W、显存频率掉档，**外部 nvidia-smi 采样也被卡 2.3s**——驱动级内存管理停摆，
  不限于本进程；
- 压力球在显存最高水位（7572 / 7461MiB）churn 后**两次段错误**（exit 139），
  与 2026-09-25 生产段错误同型——停摆的升级形态。

### 结论（C 类，条件成立）

**8GB 卡显存逼近上限（实测 >7.4GB）时，~600MB 级显存分配/释放 churn 触发驱动级
停摆 0.4~2s**：本进程全部 GPU 上下文（两个 DML 会话、WGC 采集）冻结，停顿打在
当刻持锁/排队的那个会话上（感知或深度随机），停摆窗口内采集断流；可升级为
用户态驱动段错误。稳压（无 churn）只翻倍基线不打尖峰；CPU/GIL 压力非必要条件。

### 生产观测与解读撤回记录（2026-11-07 晚，gpu.jsonl 实测）

显卡采样上线后首场（20261107_185206）captured 停顿一次，生产解读据此两次修订。

**观测事实（保留）**：

- 对局全程显存 3.75~3.8GB/8188MiB，与离线无游戏基线几乎一致 → 游戏/模拟器
  基本不占本独显；
- 停顿拍：感知单次 1160.9ms（常态 7.7ms）；同刻 SM 频率 2775→210MHz、功耗
  52→7.5W、外部 nvidia-smi 调用 62→844ms；CPU 侧（落盘/控制）正常；
- 整场 139 拍 134 拍满频——事件一场一次，多在发车后 13~35s；
- 生产五次以上停顿零内核 nvlddmkm 记录；全天唯一一条（17:59:48，Id 153
  "Error occurred on GPUID"）恰为离线 V7b 复现停顿时刻。
- 同夜续跑（20261107_194206，9 场 18 段 15199 拍，现场抓拍在位、直跑仓库代码）
  零停顿：感知在飞最长 139ms、深度 forward 最长 118ms、慢 forward 锁存零条，
  显卡全程未低于 1620MHz；外部条件与停顿场同（未重启、温度 50~62℃、显存
  3.8GB 水位、同 AC 供电）。哨兵沉默经这三条独立计时交叉验证为「真没停顿」，
  不是漏抓。未复现不归因于仪器修复（修复只动取证面、未动推理路径）；触发器
  仍未明，事件间歇。

**已撤回的解读（留痕，均为归因错误）**：

1. ~~「显存近上限分配突发触发」~~——生产显存无压力，出局；它只是离线复现的
   构造条件，不是生产触发条件；
2. ~~「独显深低功耗态转换（打盹）」~~——机器级解释，与「其他游戏/计算任务
   从未出现 ~1s 冻结」的经验事实矛盾；且离线复现的是硬失败形态（内核事件 +
   段错误），生产是无痕软停顿，触发器不同、未复现；
3. 频率/功耗塌陷的因果方向存疑（原因 or 停顿的无负载后果，210MHz 上 93% 利用率
   不似正常打盹）——不再作为结论使用。

**现存方向性事实**：问题在「NVIDIA 驱动 × 我方 DML 负载形态（计算型、无
present）」一层；生产触发器未明。归因瓶颈 = 案发中证据缺位（常规采样只能拍到
恢复期）。现场抓拍已在生产位（真源
`maaracing_master/plugins/speedrush/gpu_probe.py`）：持锁 DML 调用按线程登记
在飞，最久一条超阈即另起线程落 `trace/stall_*.txt`——我方全线程栈先落，再取
节流原因位与每进程 GPU 引擎占用；文件自带「栈抓拍时 / 外部取证结束时是否仍
在飞」两行自审，据此区分案发中证据与恢复后状态。盯梢与常规采样分线程，外部
调用被停摆卡住时互不拖累。待一场停顿按三问判决（节流类型 / 他进程占卡 /
我方线程卡点）；三样都无异常转 ETW/GPUView 调度级取证。待办与进展住
GitHub issue #18。

缓解方向随之作废：~~独显保活~~（基于已撤回的打盹假设，未实施即废）；显存
减压降级为次要。

### 首份生产现场（20261107_203426，人工录制局阶段 1，发车后 22s）

抓拍仪器修复后首次触发，现场文件 `trace/stall_203520_804_moge.txt`。本次受害者是
深度（此前几次是感知），与离线复现「停摆打在当刻持锁的那个会话上」一致。

**实测（三个独立仪器互证）**：

- 深度 forward 1004.9ms（慢 forward 锁存），常态 55~120ms；控制拍感知等锁
  928.5ms，控制环丢拍约 1.3s；
- 现场栈在「在飞 662.7ms」时落盘，确在案发中：深度 worker 停在
  `run_with_iobinding` 原生调用内，控制拍停在 DML 锁等待，其余线程均在队列等待。
  HUD 的 OCR 线程走 CPU 后端（rapidocr 的 `use_dml` 默认 false、本仓未覆盖），
  不构成锁外并发 DML；
- 节流原因位（查询窗口 20:35:21.242→21.523，完全落在停顿内）：Performance State
  **P8**，**SW Power Cap Active**、**SW Thermal Slowdown Active**，Idle Not Active，
  HW Slowdown / HW Thermal / HW Power Brake 均 Not Active；
- 每进程占用（查询窗口跨到恢复点，判读打折）：nvcontainer.exe sm 47% / mem 33% /
  **enc 13%**，wallpaper64 sm 10%，游戏本体 sm 6%；
- 独立标尺：SM 2775→210MHz、功耗 51.6→9.15W、外部调用 187→906ms、util 读数 91%，
  显存平坦 3918MiB、温度反降 56→52℃——与 18:54 感知停顿同签名。

**判读（未收口，因果方向未定）**：P8 / 210MHz / 9W 既可能是「驱动先压档导致
提交不执行」，也可能是「提交因故迟迟不执行 → GPU 无活可干 → 掉档」，0.5s 级采样
分不出先后。util 是采样窗口内内核执行时间占比（不是队列深度），且该次调用本身耗时
906ms、窗口跨越停顿前的正常段，不能读成「排队未执行」。SW Thermal Slowdown 的官方
语义是 GPU/显存温度限制，结温 52℃ 让典型过热解释不成立，但据此反推「平台/CPU 热
策略」同样无依据；计数器是累计值不是本次时长。

**同窗 CPU 侧也异常**（纯显卡降频故事覆盖不了）：该次观测预处理 67.6ms，而全场
514 个样本 p50 7.4 / p99 11.2ms；同窗控制链 36.3ms（常态 ~5）、感知 run 82.8ms
（常态 ~8）。系统 CPU 全程 93~100%（无停顿的阶段 2 同样高）、本进程稳定 ~520%，
故高负载是背景压力不是触发器。进程被 OCR 绑核限制在 12 核中的 8 个 P-core（该绑定
是 2026-08-13 A/B 验证过的修复，治 E-core 漂移造成的 1~2s OCR 尖峰，取消有已知回归
代价）。显存平坦，离线复现的 churn 机制在生产再次排除。

**取证缺口与补位**：逐线程 CPU 时间原是 1s 粒度、窗口跨在停顿前后，分不出「就绪
队列排队」与「阻塞等待」。现已在停顿现场内置窗口内双采样（复用
`core/thread_probe.py::thread_times`，零新依赖）：推进且栈不变 → 原生调用内自旋/做
CPU 工作；不动且栈不变 → 阻塞。再细的分流（CPU 就绪 vs GPU 队列、提交 vs 执行）走
ETW 包裹采集，见下节。

## 真业务回放台（replay_business.py）

`repro.py` 自包含重建 DML 调用面、不 import 业务代码，它证的是「只把推理循环起来
不复现」；但那一轮变量集里没有真业务的并发线程组，阴性结果的排除力只到它覆盖的
那一组。`replay_business.py` 补这一层：磁盘供帧替身注入驾驶环的采集协议
（`ctx.capture.frame_with_age()` 四元组），录制模式装配真控制链，于是控制环（感知
DML）、深度链（MoGe DML）、深度调试、HUD 采样与落盘、车道观测、录制帧编码落盘与
手柄采样、调试落盘、两条流水汇、性能采样器、显卡探针全部按生产形态起线程。选录制
模式是因为它不 acquire 手柄、不要求窗口独占，最省伪造，而生产停顿正是在人工录制局
复现的。

供帧语义与中心采集缓存对齐：独立线程按录制时的真实帧间隔解码发布，消费者读最新帧。
在消费者线程里按需解码会把解码成本算到控制环头上，等于又少控一个变量。

**变量集纪律**：每次运行落 `replay_fidelity.json`，逐项声明覆盖与未覆盖。当前未覆盖
的是 WGC 采集线程、真实游戏窗口与模拟器进程、物理手柄输入（采样线程照跑但 pads 为
空）、导航图模板识别、桌面合成呈现负载。**未覆盖项存在时，阴性结果只排除已覆盖的
那一组**，不得写成「排除了业务侧」。

标尺独立于业务代码（C 类硬约束）：复现判据要现场抓拍（含 Win32 线程 CPU 时间增量）
与外部 nvidia-smi 调用时长同窗佐证，不只看业务自己的计时。

用法（仓库根）：
`.venv/Scripts/python.exe tools/experiments/dml_stall_repro/replay_business.py --seconds 180`
素材缺省取首份生产现场那一局，`--session` 可换；产物落用户数据目录，不入库。

**首轮结果（2026-11-07）**：180s / 2854 拍 / 16.1Hz，未复现，且是**有效阴性**——
负载画像与生产停顿局对齐：本进程 CPU p50 455% vs 生产 493%、系统 CPU 75% vs 68%、
显卡 util 51% vs 60%、感知 run p50 8.4 vs 7.9ms、深度 forward p50 51.1 vs 53.6ms、
拍率同为 16.1Hz；显存反而更高（4531 vs 3964MiB）。线程面只缺宿主侧三条（模块
worker、调试流、模型预载），已列入未覆盖声明。

此前一轮 180s 是**无效阴性**：供帧跨轮复用原始帧号 → 新鲜度守卫判旧帧 → 驾驶环
36s 后静默停产拍，而显卡探针照采满全程，看起来像「跑满三分钟没复现」。故本台跑完
强制自审产拍率与覆盖时长（低于 10Hz 或未覆盖请求时长 80% 即判无效、非零退出），
帧号跨轮单调递增。

事件本身间歇（生产上午 6 场 5 次、晚间 9 场 0 次、录制局 1 次），单轮 180s 的阴性
排除力有限；未覆盖的五项仍是候选。

**接真识别负载后离线首次复现（2026-11-07 22:23，commit 01d1574）**：`--graph real`
让真 NavGraph 的 probe 真跑模板匹配（CPU 负载与调用节奏在场），壳把阶段退出判定与
匹配结果解耦（真匹配对窗口几何敏感：齿轮偏约 10px 即 ROI 0 分、阶段秒退，复现台
寿命不该押在匹配成败上）。接上后 30s 冒烟即复现 `stall_222311_085_yolo.txt`（感知
在飞 645ms）；此前 live+stub 累计约 10 分钟匹配负载零复发。**模板识别负载是把现象
压出来的候选变量**，待 real/stub 对照轮确认。

**对照修正（22:26 / 22:30 各一轮 240s）**：real 与 stub 两臂均未复发（16.0Hz 有效
阴性）。故识别负载作为触发变量**未坐实**——22:23 那次 30s 复发是概率性事件，单轮
对照功率不足，候选权重回落。主线仍是 CPU 争抢信号（见下）；复发概率性意味着任何
单变量结论都需要多轮重复，不得以一轮复发/一轮阴性定论。

**现场分流证据（线程 CPU 时间双采样首次生效）**：卡住的感知线程在 171.8ms 墙钟里
吃 140.6ms CPU（81.9%）→「持续占用 CPU 执行，不支持被阻塞」。这排除两种解释：
OS 就绪队列排队（那会 CPU 时间不增长）、被动睡等 GPU fence（ likewise 不增长）。
指向原生 DML 调用内部的 CPU 侧工作或其自旋等待。同窗系统 CPU 98% 而本进程仅
312%（背景进程争抢显著）；显卡仍 P8 + SW Power Cap / SW Thermal Active、Idle Not
Active。栈同窗还有车道与 OCR 两条 CPU 侧 ORT 推理在跑、深度调试在渲染。

**判读边界**：CPU 时间增长只证明「在占用 CPU」，不证明是驱动自旋还是提交链 CPU
工作；若后者被背景争抢拉长，与「GPU 不执行导致 CPU 自旋」仍须 ETW 区分提交与执行。

## ETW 包裹采集（capture_etw.ps1 + dml_stall.wprp）

管理员 PowerShell 跑 `capture_etw.ps1`（本机 UAC 自动提权，可从普通 shell 经
`Start-Process -Verb RunAs` 拉起）：自定义 profile 起 CPU 调度（进程/线程/模块加载、
上下文切换、就绪队列、采样 IP，不抓栈控体量）+ DxgKrnl 全关键字采集，循环跑
live+real 回放（每轮上限 240s、收尾挂死超 330s 即杀），**一发现新停顿现场立即
`wpr -stop`**——不等回放收尾，防环形缓冲把停顿窗口覆盖掉；四轮未复发则 cancel 不落盘。

采集走**内存环形缓冲**（两收集器各 1GB）：录制期间不落盘，stop 才写
`%TEMP%\maar_stall_<时刻>.etl`。内置 profile 加 `-filemode` 实测约 2 分钟写 15GB，
小余量磁盘扛不住；内存模式的代价是只保留最近数十秒，故停采集必须贴着停顿现场。

解码：tracerpt CSV 与 Get-WinEvent 对本 ETL 均丢调度载荷（见下「解码工具事实」），
可用路径为 TraceEvent 临时工程。判读目标：停顿线程在窗口内的调度状态（在跑/就绪
未排上/等待）三分，与 GPU forward 是否拉伸对照，分流「提交链 CPU 工作被争抢拉长」
与「GPU 不执行导致 CPU 自旋」。

阻塞等待的对象**未定**，不能命名为锁 convoy：MoGe 路径先 `LOCK.acquire(blocking=False)`
（抢不到抛 Busy 跳帧、不等待）再 `RUN_WATCH.enter` 再 forward，故在飞期间 MoGe **持有**
全局 DML 锁，它自己的 Waiting 不可能是等同一把 Python 锁，只能是原生 DML 内部同步 /
GPU fence / 内核对象；「yolo/lane 等 MoGe 释锁」的 convoy 是**传播**机制，与 MoGe 自身
等待的**发生**机制须分开（wait reason / 切换栈 / 唤醒事件待取）。
