# lane_model_efficiency — 线观测模型为什么吃算力、怎么跑到最高效率

## 背景

线观测用的是 TwinLiteNet+ 的 `small` 配置（微调权重，12.2 万参数 / 0.54MB），
输入 384×640，目标 20Hz。生产测量（见 `lane_obs_dml` 实验）每帧 37~39ms、
跑图时约 2.2 核；用户疑问：这么小的模型为什么这么吃算力，能不能按原论文的思路
跑到最高效率。

## 原论文事实（TwinLiteNet+，arXiv 2403.16958）

四个配置，参数量与 FLOPs（论文口径，BDD100K，640×360）：

| 配置 | 参数 | FLOPs | 可行驶区 mIoU | 车道 IoU |
|---|---|---|---|---|
| nano | 34K | 0.57G | 87.3 | 23.3 |
| **small（现役）** | **0.12M** | **1.40G** | **90.6** | **29.3** |
| medium | 0.48M | 4.63G | 92.0 | 32.3 |
| large | 1.94M | 17.58G | 92.9 | 34.2 |

架构：ESP 编码器（标准卷积 + 深度可分离空洞卷积）+ CAAM 注意力 + 双解码器
（可行驶区 / 车道线）。论文的部署结论是「INT8 / FP16 量化稳健、嵌入式设备上
延迟与功耗友好」，效率来自架构本身（深度可分离 + 空洞卷积），不是导出技巧。

## 要回答

1. 这个 0.54MB 模型的算力花在哪一层；
2. 不重训的前提下，哪种运行时配置效率最高（CPU / DML / FP16 / INT8）；
3. 继续降算力需要动哪里，代价是什么。

## 方法

`probe_model_efficiency.py`（自包含）：

- ① 用 ONNX shape inference 逐节点估 Conv/MatMul MAC，按 `da`/`ll` 输出做祖先
  归账，找出算力集中层；
- ② 同一真帧上测 CPU 4 线程 fp32、DML fp32、DML fp16（`onnxconverter_common`
  现场转换）、静态 INT8（`onnxruntime.quantization` QDQ，12 帧校准）的 p50/p95；
- ③ 以 CPU fp32 为基准，对 12 帧统计 softmax 概率最大差、均值差与阈值 0.30 的
  像素翻转率；
- 启动即退出 Windows 能效节流（否则 4 线程延迟会虚高数倍，见 `lane_obs_dml`）。

## 结果（2026-11-13，RTX 4060 Laptop / 12 逻辑核，真实对局帧）

### 算力分布（Conv/MatMul MAC，按 2×MAC 计 GFLOP）

| 项 | GFLOP | 占比 |
|---|---|---|
| 模型总计 | 2.50 | 100% |
| 共享主干（ESP 编码器 + CAAM） | 2.04 | 81.5% |
| 仅可行驶区分支 | 0.23 | 9% |
| 仅车道线分支 | 0.23 | 9% |
| **单层 `/encoder/b2/conv`（67→67，3×3，96×160）** | **1.24** | **49.5%** |
| `/encoder/b3/conv`（32→32，3×3，48×80） | 0.28 | 11% |
| `/encoder/b1/conv`（11→16，3×3，192×320） | 0.20 | 8% |

`b1/b2/b3` 是三个跳连合并处的**标准卷积**（论文为保精度保留，没有换成深度
可分离）；其中 `b2` 一层就占全模型一半算力。

### 推理配置（同一帧，p50/p95；偏差对 12 帧汇总）

| 配置 | p50 / p95 | 相对 CPU | 最大概率差 | 均值差 | 翻转@0.30 |
|---|---|---|---|---|---|
| CPU 4 线程 fp32（现役） | 23.2 / 36.8 ms | 1.0x | — | — | — |
| DML fp32 | 6.3 / 8.5 ms | 3.7x | 0.0000 | 1.3e-08 | 0.000% |
| **DML fp16** | **3.7 / 5.4 ms** | **6.3x** | 0.057 | 5.4e-05 | **0.005%** |
| CPU 4 线程 INT8（静态 QDQ） | 36.5 / 38.7 ms | 0.6x | 0.98 | 2.9e-03 | 0.303% |

### 离线回放：fp32 vs fp16 的线候选（连续真帧，过 rms≤3px 质量门）

| 会话 | 帧数 | 原始线数不一致 | 过门后不一致 | 匹配线对 | 横位 \|ΔL\| p50 / p95 / max | 超 0.02 道 | 残差 \|Δrms\| max |
|---|---|---|---|---|---|---|---|
| 20261109_104823_manual_p2 | 876 | 25 帧（2.9%） | 23 帧（2.6%） | 2566 | 0.0002 / 0.0012 / 1.02 道 | 10 对 | 1.9 px |
| 20261109_104823_manual_p1 | 734 | 22 帧（3.0%） | 24 帧（3.3%） | 2060 | 0.0001 / 0.0012 / 0.34 道 | 9 对 | 2.2 px |

97% 的帧两套模型提取出的线完全一致；剩余帧是阈值附近的碎片线多一条/少一条，
个别帧因野线替换真线出现整道级偏差。匹配上的线 99.6% 横位差 <0.02 道。

## 结论

1. **模型本身没有异常**：「small」在论文口径下就是 1.40 GFLOPs；20Hz 等于每秒
   28~50 GFLOPs 的持续负载，CPU 上 23ms/帧（4 线程）是这类模型的正常量级。
   0.54MB 只是权重小，算力由 384×640 的分辨率与通道数决定。
2. **不重训的最高效率是 FP16 + DML**：3.7ms/帧，是 CPU 的 1/6、fp32 DML 的 1/2；
   12 帧输出最大概率差 0.057、超过 0.3 阈值翻转 0.005%（约 1/2 万像素）。
   但离线回放显示它不是逐帧等价：约 3% 的帧线候选条数变化、19/4626 对线横位差
   >0.02 道（个别整道级）。能不能直接换，取决于这些边角帧会不会影响线锁—
   ——这一项可以继续离线验（同一段帧 + 录制的深度锚喂 `LineTracker` 对比），
   不需要实机对局。
3. **INT8 在本栈上是负优化**：ORT 静态 QDQ 后 36.5ms（比 fp32 慢 57%），且最大
   概率差 0.98、翻转 0.3%。论文的 INT8 稳健性依赖其部署栈（TensorRT 等），
   不能直接搬到 onnxruntime-directml。
4. **再降只能动模型**（都要重训 + 评估）：
   - `b2` 换成深度可分离卷积：约 -43% FLOPs（-1.08 GFLOP），改动最小、收益最大；
   - 换 nano 配置：0.57G（约 -60%），但论文车道 IoU 从 29.3 掉到 23.3；
   - 重导出 360×640（去掉 12px 灰边）：约 -6%，需重导出与精度校验。
5. 结合锁争抢实验：FP16 DML 持锁 3.7ms/帧，20Hz 时 GPU 锁占用约 7%（fp32 DML
   为 12%），对深度的挤占比 fp32 DML 更小。

## 边界

- 精度对比是「概率差 + 线候选差」，不是车道 IoU；回放覆盖两个会话 1610 帧，
  都是同一场景（白天、保险杠视角），换天况/机位要另取样。
- 算力是 Conv/MatMul MAC 的估算（不含 BN/PReLU 等逐元素），与论文的 FLOPs 口径
  不同；两者只看量级与内部占比，不直接互比。
- `b2` 深度可分离、nano、360×640 三项只给了算力预期，没有训练与精度数据。
- DML 延迟受 GPU 负载影响；本机测试时游戏与 IDE 同期在跑，绝对值按本机当时状态读。
