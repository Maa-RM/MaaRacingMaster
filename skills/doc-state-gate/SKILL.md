# 现状文档落笔闸

现状文档指描述「现在怎么工作」的正文：README、模块文档、功能文档、业务文档、接入文档、CODE_WIKI、docs/ 下的 L1~L3 文档。它们只允许描述当前状态。本闸是 AGENTS.md 知识路由（L0~L4 信源等级、「过程叙述不进 L1~L3」）在写文档动作上的执行细则。

**主判据：写下的每句话，在删掉今天的临时文档、忘掉本次会话、换一台机器之后，必须仍然独立成立。**

「换一台机器」指的是：换一个协作者、换一套本机环境，这句话仍为真。仓库正文是团队共享的当前状态，不是某一台机器的工作台账；只对某台机器成立的事实属于本机层，不属于正文。

不成立的典型形态：阶段叙事（「阶段一加了X」）、变更记叙（「原来是A，某时间点改成B」）、幽灵未来愿景（「为了未来X设计理念」）、只有读过本次会话才懂的指代、只对某台机器或某个 harness 成立的本地事实（下文「机器与项目的边界」）。

## 落笔前自答（逐段）

1. **现状还是过程？** 试过什么、何时改的、为什么改、阶段N做了什么，都是过程，不进正文。去向：决策理由 → `docs/adr/`；时间线与「做了什么」 → git commit 与 `docs/update_log.md`；尚未落地的方向 → plan。
2. **有「原来…现在…」句式？** 只保留「现在」半句；行为变更的对比与理由住 ADR 或 commit message。
3. **理由是否依赖未来？** 现状不得用「为了未来的X」解释现在的结构；愿景住 plan/ADR。确实留了扩展缝，用「当前支持什么、扩展点在哪」的句式写。
4. **数值与清单是不是第二份副本？** 可机检的数值、枚举清单只写指向真源的路径（数值禁令），不复制数值本身。
5. **读者能不能不读代码就看懂？** 业务文档用业务语言；代码块与技术名词只在「没有它这句不成立」时出现，且保持最小。
6. **这句话是给谁看的？** 讲正文自己（段次、落点、为什么写在这里、待裁决的选项）的句子只对本次会话成立：需要长期留的写成一句「本条住哪个 home」的指针，其余当场问一次或落 issue，不留在正文里等读者反推会话。plan 可以承载未落地的方向，但它一旦被提炼，这些句子会跟着搬进现状文档。
7. **这句话在哪一层成立？** 换个协作者、换套本机环境还成立吗？不成立的就是本机事实，去向见下节「机器与项目的边界」。判据是「这句话描述的是项目本身，还是我这台机器的环境」，不是「这句话有没有用」——本机事实往往很有用，只是不属于仓库正文。

## 机器与项目的边界

仓库正文（L0~L3、README、CODE_WIKI、技能定义）描述的是**项目本身**：换一个协作者 clone 下来仍然成立的事实、约定与路径。本机层描述的是**这台机器怎么把项目跑起来**：绝对路径、本机环境缺口、harness 特有的加载位置与启动参数、个人工具链版本与临时绕法。两者都会腐坏，但混入正文的那一层会让所有读者读到只对他们不成立的描述。

**判据**：把这句话给一个从零 clone 仓库、用标准环境的协作者看——他能据此行动吗？路径是他机器上的路径吗？工具版本是仓库声明的还是你本机恰好装的版本？命令是可移植的还是依赖本机目录结构 / 环境变量？任一是否定的，这句话就是本机事实。

**去向**：

| 事实性质 | 写在哪 | 不写在哪 |
| --- | --- | --- |
| 项目约定、仓库相对路径、仓库声明的解释器与验证入口 | 仓库正式文档（对应 Lx home） | — |
| 本机绝对路径、本机工具链版本与缺口、harness 加载位置与启动参数、个人绕法 | gitignore 的本机个性化文件、harness 注入的本机规则、工作区记忆 | 仓库正文、技能定义、commit message、对外 PR / 交付物 |
| 需要全团队知道但会随本机变化的配置入口（如「本机个性化文件放哪、怎么被读取」） | 仓库正文只写**入口约定与相对路径**，不写具体值 | 仓库正文写具体本机值 |

**与隐私红线的分工**：AGENTS.md 红线 4 管「不能写」（密钥与本机绝对路径属于禁止项，无论写在哪一层）；本节管「写在哪一层」——同样一条环境事实，写在本机层是正常的工作台账，写进仓库正文就是错误归属。两者独立成立：隐私检查通过不代表归属正确，归属正确也不豁免隐私检查。

**跨会话误判的两种典型**：一是把「本机 harness 怎么加载技能」写进技能定义——加载位置随工具约定而变，技能只声明自己是权威、副本由各 harness 自行核对；二是把「本机 Python 是哪个版本、仓库该用哪个解释器」写成一句——仓库只声明它要求的版本，本机恰好装了什么属于本机层。

## 代码收尾时的文档同步

改完某模块的代码、准备收尾时，顺带核对该模块 `CODE_WIKI` 的索引段与表格段（类索引、方法表、常量表、坑点表）是否还与代码一致：删除或改名的符号要从表里消失或改写，新增的公开入口要补上。索引段写的是「现在有什么」，代码一变它就可能成为旧接口的展示窗。

## 临时计划/阶段文档的收尾

阶段性任务文档是消耗品，收尾时内容二选一（「留在原地」不是选项）：

- **折进现状**：仍然成立的结论按目标 home 的句式**整段重写**并入，不在旧措辞上逐词删改——写「现在如何」，不写「阶段N加了什么」；
- **删除**：其余内容直接删，历史由 git commit 与 ADR 承载。

完成后 grep 仓库：确认没有指向该临时文档的路径引用、没有「阶段N」式断头字样残留。

## 交付前自查

对本次会话写过的每一份**现状文档**（plan 类过程文档不在此列），假设读者只知道「现在的代码」：

- 逐句检查是否独立成立；「阶段」「原来」「之前」「目前先」「后续会」是过程残留的信号词，「此处不该放」「位置待定」「要么 A 要么 B」「建议另立」是元叙述与归属错位的信号词，命中即核对该句该改写还是迁走；
- 过一遍机器维度：绝对路径、用户名与本机目录名、具体工具版本、harness 专有目录与启动参数、「本机」「当前环境」限定语，命中即按「机器与项目的边界」决定改写为项目口径还是迁去本机层；
- 从 plan 提炼过来的段落，整段按目标 home 的句式重生，不逐词删改——落笔时的会话性说明最容易跟着搬进来；
- 临时任务文档已折叠或删除，无断链引用。
